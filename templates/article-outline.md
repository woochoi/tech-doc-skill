# 기술 블로그 문서 뼈대 템플릿

새 글을 시작할 때 이 구조를 복사해서 채운다. 모든 섹션이 필수는 아니지만, ★ 표시는 거의 항상 둔다.

```markdown
# (제목: 검색 키워드 + 클릭 이유가 같이 보이게)

(한 줄 설명: 이 글을 읽으면 무엇을 알게 되는지 1문장)

읽는 시간 약 N분 · 출처: (공식 문서/레퍼런스 링크)

## 이런 분을 위한 글입니다   ★
- (대상 독자 1~2줄)

## 읽고 나면 이렇게 달라집니다   ★
- (구체적 변화 1~2줄)

> 이 글의 성공 기준: 다 읽고 나서 ______ 할 수 있으면 성공입니다.

---

## (질문/공감으로 여는 도입)   ★
- 독자가 겪는 문제를 한 문장으로
- 왜 지금 이 주제가 필요한지

---

## (핵심 개념 1: 비유 먼저, 정의 그다음)   ★
- 쉽게 말하면 ~에 가깝습니다
- 공식 문서에서는 ~라고 설명합니다 (사실)
- (비교가 필요하면 표)

## (핵심 개념 2: 원리 — 왜 그렇게 동작하는가)   ★
- 메커니즘 설명 (비유 → 동작 → 그래서 뭐가 좋은가)
- (코드/설정 예시 + 결과 해석 한 줄)

## (실무 적용 / 흔한 함정)
- 나쁜 예 / 좋은 예 대비
- 자주 하는 실수

---

## 정리하면   ★
- 본문에 나온 핵심만 압축 (새 내용 금지)
- (요약 표 또는 짧은 코드블록)

## 오늘 바로 할 수 있는 것   ★
- 독자가 5~10분 안에 시도할 작은 행동 1개

## 다음 편 (시리즈일 때만)
- 다음 글 제목 + 한 줄 예고
```

## 제목 잘 짓기 (나쁜 예 / 좋은 예)

```
나쁜 예
Kafka의 이해와 중요성
```
```
좋은 예
Kafka Consumer Group이 메시지를 나눠 갖는 원리 (입문편)
```

추상적 명사 나열 대신, **무엇을 / 누구 눈높이로** 가 드러나게 한다.
