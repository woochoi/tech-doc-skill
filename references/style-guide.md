# 기술 불로그 스타일 세부 가이드

`SKILL.md`가 "무엇을 하라"라면, 이 파일은 "어떤 톤과 문장으로 쓰는가"의 세부 기준이다.

## 1. 목소리(voice)

- **존댓말 평서체(~입니다 / ~합니다)** 를 기본으로 한다.
- **독자를 옆에 앉혀두고 설명하는 톤.** 가르치되 위에서 내려보지 않는다.
- 독자의 불편을 먼저 인정한다. "한두 번은 괜찮습니다. 그런데 매번 반복하면 금방 귀찮아집니다."
- 겁주지 않는다. "처음 보는 문법이라도 겁먹을 필요는 없습니다. 뜻은 단순합니다."

## 2. 문장 패턴 (이 표현들을 적극 쓴다)

| 용도 | 표현 예시 |
| --- | --- |
| 개념을 쉽게 환원 | "쉽게 말하면 ~에 가깝습니다." |
| 비유 도입 | "비유하면, ~" |
| 정의를 부드럽게 | "~라고 부릅니다.", "~정도로 이해하면 됩니다." |
| 공식 사실 인용 | "공식 문서에서는 ~라고 설명합니다." |
| 해설 전환 | "여기서부터는 우리 상황에 적용한 해석입니다." |
| 안심시키기 | "처음부터 완벽할 필요는 없습니다." |
| 행동 유도 | "오늘은 딱 하나만 해보면 됩니다." |

## 3. 피하는 문장 (번역투·추상어)

- "~에 의해 처리되어집니다" → "~가 처리합니다"
- "~하는 것이 가능합니다" → "~할 수 있습니다"
- "본 문서에서는" → "이 글에서는"
- "원문에서는" 반복 → "공식 문서는", "Spring 팀은"처럼 주체를 직접 지칭
- "매우 중요합니다" 같은 빈 강조 → 왜 중요한지 한 줄로 보여준다

## 4. 시각 장치 사용 규칙

**표 (table)** — 개념을 나란히 비교할 때. 보통 `구분 | 쉽게 말하면 | 예시` 3열.

**코드블록** — 복붙해서 바로 쓸 수 있는 것만. 설정 파일, 명령어, 코드, 프롬프트.
개념 비교나 설명 문장은 코드블록에 넣지 않는다.

**강조 박스(인용문 `>` 또는 소제목)** — 한 섹션의 결론을 한 덩어리로 묶을 때.
예: `> 핵심: config는 필수가 아닙니다. 매번 같은 답을 반복할 때 쓰는 선택지입니다.`

**나쁜 예 / 좋은 예 대비** — 코드블록 두 개를 나란히. 라벨을 붙인다.
```
나쁜 예
좋은 예
```

**구분선(---)** — 큰 섹션 사이마다 넣어 호흡을 끊는다.

**채워넣기 문장** — 독자가 직접 적게 만든다.
"나는 ________를 자주 만든다. 이때 항상 ________ 기준을 지켜야 한다."

## 5. 분량·리듬

- 한 문단은 1~3문장. 핵심 문장은 단독 한 줄로 띄운다.
- 소제목은 동작이 보이게. "캐시" (X) → "캐시를 왜 무효화해야 하는가" (O)
- 섹션마다 "예시 1개 + 적용 1개"를 최소 보장한다.

## 6. 깊이를 지키는 법 (입문용이라고 원리를 버리지 않는다)

쉽게 푸는 것과 얕게 쓰는 것은 다르다. 입문자용이어도 **"왜 그렇게 동작하는가"** 는 남긴다.

- 나쁜 예: "Redis는 빠릅니다. 캐시로 쓰면 좋습니다." (왜인지가 없음)
- 좋은 예: "Redis는 데이터를 디스크가 아니라 메모리에 둡니다. 메모리는 디스크보다 읽고 쓰는 속도가 수십~수백 배 빠릅니다. 그래서 자주 조회되는 값을 Redis에 올려두면 DB까지 가지 않아도 됩니다."

원리를 설명할 때도 비유 → 메커니즘 → 결과(그래서 뭐가 좋은가) 순서를 지킨다.
